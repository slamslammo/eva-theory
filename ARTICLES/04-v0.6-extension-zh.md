# v0.6 为 EVA 增加了什么

*面向读者解释 v0.5 core architecture 当前扩展的指南。*

English: [04-v0.6-extension.md](04-v0.6-extension.md)

---

**关于本文。** 本文面向已经理解 EVA 基本 framing 的读者，解释 `THEORY/v0.6-extension.md` 的作用。它不替代正式 v0.6 文本。它的目标是用更直接的架构语言说明：v0.6 增加了什么，为什么需要这些增加，以及它与 v0.5 的关系。

一句话：

> **v0.5 定义核心骨架。v0.6 解释当 EVA 进入更丰富环境时，这个骨架如何保持稳定。**

v0.6 不替代 v0.5。它扩展 v0.5。

当前公开文本采用 unified release 形式：`THEORY/v0.6-extension.md` 将 v0.6 base 与 v0.6.1 对 rate sensing、exploration、memory layering 和 L3 inherited priors path 的 refinements 合并呈现。

---

## 1. 为什么需要 v0.6

v0.5 建立了 EVA 的中心架构：continuous existence 作为 first-order framing、L1-L3 core、drive as contextual broadcast、anchor as pre-generative constraints、mediated release，以及通过 outcome 进行 learning。

这个核心是稳定的。但一旦理论被应用到狭窄 baseline runtime 之外，就会出现新问题：

- 到底什么应该 persist？
- 架构应如何处理来源不同的 capabilities？
- 系统中哪些部分是 structural invariants，哪些是 scenario-specific content？
- 当单个 action 同时产生多种后果，outcome 应如何表示？
- 不声称访问 inner essence 的情况下，stability 如何评估？
- 当 EVA 进入新环境时，默认应做什么？

v0.6 回答这些问题，同时不重写核心。

它最好被理解为一种 extension discipline：它告诉后续工作如何扩展理论，同时避免每个新环境都变成新理论。

---

## 2. Active persistence

v0.5 谈 continuous existence。v0.6 将其 sharpen 为 **active persistence**。

Persistence 不意味着冻结当前状态。一个拒绝变化的系统，在环境变化时仍可能无法 persist。对 EVA 来说，persistence 意味着维护 future viability：在变化条件下继续作为同一个 agent 存在的能力。

这很重要，因为 inaction 并不自动安全。在有 metabolic cost、resource pressure、environmental risk 或 expiring opportunity 的环境中，什么都不做可能比 bounded action 更损害 future viability。

因此 active persistence 给 EVA 的原始问题一个更精确读法。问题不只是“agent 如何继续？”而是：

> 为了让 agent 在时间中保持自己，什么必须改变，什么必须保持 invariant？

---

## 3. Persistence targets

如果 persistence 重要，下一个问题就是：persistence 的 target 是什么？

v0.6 的回答不是一个模糊的 survival objective，而是一套 persistence target hierarchy。它区分七个 level：substrate instance、embodied instance、capability structure、resource and asset system、reproductive structure、group structure，以及 cultural information。

这很重要，因为不同 level 的 failure 不是同一种 loss。embodied instance 可以失败而 capability 仍然保留；resources 可以崩塌而 agent 本身仍然完整；group 也可以解体而 individual agents 继续存在。这个 hierarchy 为 EVA 提供了表达 cross-level trade-off 的 vocabulary，也让 deployment 可以明确哪些 persistence levels 处于 active 状态。

它不意味着每个 implementation 都必须激活全部七个 level。它意味着在 specify scenario 时，应明确声明 relevant persistence targets。

---

## 4. Capability provenance

v0.6 也追问 capability 从哪里来。

正式扩展文本区分五类：structural invariants、existence-field conditions、designer-given prior capabilities、individually acquired capabilities，以及 inherited priors。

这些类别不等价。它们在 origin、modification permission、provenance requirement 和 identity implication 上都不同。Learned habit、designer-given prior 和 inherited prior 不应因为都会影响行为，就被赋予相同 authority。

tool outputs 和 external models 在 v0.6 中很重要，但它们不是第六种结构性 capability source。它们提供的是流经架构的 operational content，并且必须保留 provenance。

因此 capability provenance 是 stability concept，而不仅是 bookkeeping。它帮助 agent 区分什么可以修改、什么应该审计、什么算自己的 learned structure，什么只是 external operational content。

这也 sharpen 了 v0.5 对 LLM 的定位：language models 可以提供有价值的 operational content，但不会变成 release authority，也不能替代 agent 自己的 memory 和 skill formation。

---

## 5. Structural invariant vs operational content

v0.6 最重要的澄清之一，是 **structural invariants** 与 **operational content** 的边界。

Structural invariants 是跨 scenario 必须保持稳定的架构承诺，例如：

- mediated release authority；
- anchor as pre-generative constraint；
- append-only learning history；
- sensing、drive、deliberation 和 release 的分离；
- drive 是 contextual broadcast 而不是 command。

Operational content 是随环境变化的具体材料：

- drive names；
- sensor dimensions；
- action vocabularies；
- anchor policies；
- outcome labels；
- prior-skill heuristics；
- scenario-specific interpretation rules。

这个边界防止理论失控膨胀。新环境通常应该通过 scenario specification 增加 operational content。只有在现有理论无法表达该环境、产生内部矛盾，或暴露边界失败时，才应该重写 structural core。

这也是配套 `eva-agent` 实现中 framework-owned structure 与 scenario-owned content 分离的理论背景。那个工程拆分表达了 v0.6 边界，但理论本身仍负责定义这个边界。

---

## 6. Multi-dimensional outcome

v0.5 已经包含 outcome、RPE 和 habit formation。v0.6 让 outcome surface 更显式。

Outcome 不应过早压缩成一个 scalar reward。单个 action 可能改善 short-term task progress，却损害 integrity；也可能保护 long-term viability，却降低 immediate performance。如果架构太早把这些 consequences 压成一个数字，就会丢失“发生了什么”的结构。

因此 v0.6 将 outcome 视为 multi-dimensional。重要问题不只是“这好吗？”而是“在哪些 dimensions 上好或坏，在什么 drive context 下，对 future viability 有什么 implication？”

这保留了 hard constraints 与 soft trade-offs 的差异。有些效果无论 reward 如何都不可接受。另一些效果可以在 current drive pressure 下权衡，并随时间学习。

---

## 7. Observable stability

EVA 讨论 continuous existence，但不需要声称能够直接访问 identity 的 inner essence。

v0.6 引入 **observable stability**：通过外部 traces 评估 continuity。例如 release boundaries、anchor behavior、capability provenance、outcome interpretation、memory updates，以及对 recurring conditions 的 response 是否稳定。

这让理论更可测试。问题从“系统是否有 metaphysical self？”转为“系统是否在变化条件下保留了定义其 continuity 的 structural commitments？”

Observable stability 不是 persistence 的全部，但它是 engineering 和 validation 可以检查的部分。

---

## 8. Scenario specification

v0.6 的 practical discipline 是 scenario specification。

当 EVA 进入新环境，默认反应不应是写一个新理论章节，而应是写 scenario document，说明：

- 哪些 persistence targets active；
- 哪些 drives apply；
- 哪些 sensors meaningful；
- 存在哪些 actions；
- 哪些 anchor policies 限制 candidate generation；
- 哪些 outcome dimensions 重要；
- 有哪些 prior skills 或 inherited capabilities；
- 应检查哪些 stability traces。

这防止理论每遇到新环境就扩张。新环境首先是工程工作。理论扩展只保留给当前 framework 无法表达、内部矛盾，或边界失败的情况。

---

## 9. 与 v0.5 的关系

v0.6 应被读作 v0.5 的 refinement 和 extension，而不是 replacement。

v0.5 core 保持不变：

- Claim A 和 Claim B；
- C1-C3 operating conditions；
- L1-L3 architectural core；
- drive as contextual broadcast；
- anchor as pre-generative structural constraint；
- action selection as peer circuit；
- L4/L5 作为 weaker downstream extensions。

v0.6 改变的是若干 v0.5 statement 的读法。“Continuous existence” 现在应通过 active persistence 阅读。v0.5 的 drive list 应被理解为 field-conditioned，而不是 universal。Skill library 应通过 capability provenance 阅读。“Grow, don't deploy” 适用于被允许 grow 的 operational content，而不适用于 structural invariants。

简言之：v0.5 给出骨架；v0.6 给出扩展规则。
